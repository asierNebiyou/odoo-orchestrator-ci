## Workstream 1 — Manifest & dependency graph engine — **done**

- **1.1 `__manifest__.py` parser (M)** — *Done.* `orchestrator-core::manifest` hand-rolls a recursive-descent parser for the Python dict-literal subset real manifests use (strings incl. triple-quoted and adjacent-concatenated, lists/tuples, numbers, `True`/`False`/`None`, `#` comments, trailing commas), with line/column error reporting — no Python runtime dependency. Extracts `name`/`version`/`category`/`depends`/`installable`/`application`/`auto_install` (including the Odoo 17+ conditional-list form). 10 unit tests, including realistic multi-field manifest fixtures.
- **1.2 Provenance-tagged dependency graph (M)** — *Done.* `orchestrator-core::modules::scan` walks every addons source for a server (in rank order), tags every module found with its source's label/kind/rank, and computes a topological install order (Kahn's algorithm) over the winning module set, with real cycle detection (tested against an actual `a depends on b, b depends on a` fixture).
- **1.3 Shadowing collision detector (M)** — *Done.* Lowest-`rank` source wins any technical-name collision, exactly matching Odoo's own addons-path resolution order; every other copy is flagged `shadowed: true`. Tested with 2-way and 3-way collisions across real directories, plus non-fatal handling of a missing addons directory and a manifest that fails to parse (both reported in the scan result rather than aborting it).
- **1.4 Wire into `orchestrator-api` (S)** — *Done.* `POST`/`GET /servers/:id/addons-sources` (register/list addons-path entries) and `GET /servers/:id/modules` (run the scan, emit `modules_scanned`). The scan runs on `spawn_blocking` since a large addons-path walk could otherwise stall the same async runtime the WS broadcast loop shares.
- **1.5 Wire into frontend Modules screen (M)** — *Done, with one deliberate scope cut.* `Modules.tsx` replaced the stub: a server picker, an addons-sources panel (add/list), a "Scan modules" action, results grouped by provenance with the SHADOWED badge, and surfaced collisions/unresolved-deps/parse-errors/cycle rather than hiding them. **Not shown:** the mock's "3 of 4 up to date" currency instrument — that needs per-database `ir_module_module` state, which needs an actual running Odoo process to query (workstream 2). Showing a fabricated version of it now would violate the project's standing "no fake progress" rule; it's queued as part of task 2.5 once 2.4 exists to source real data from.

## Workstream 2 — DB/module lifecycle

- **2.1 Embedded Postgres process supervisor — multi-instance (L)** — *Core logic, multi-instance decision, and `Core`/API/frontend wiring all done; Tauri-sidecar packaging still open.* `orchestrator-core::postgres::PgSupervisor` wraps `initdb`/`pg_ctl`/`pg_isready` (matching `odoo-orchestrator-runtime-architecture.md`'s "self-contained data directory, no service registration, no admin rights" decision) and owns a real `Stopped → Starting → Running → Stopping → Crashed` state machine: `start()` calls `pg_ctl start -w` (which does its own readiness wait) then hands off to a background health-check loop polling `pg_isready`; `stop()` calls `pg_ctl stop -m fast -w`; a generation counter stops a stale watcher from a previous run clobbering a fresh one; a `with_listener` hook fires on every transition (including a crash the health watcher detects on its own) without polling. Also includes a real, tested, Unix-only privilege-drop feature (`run_as: Option<(uid, gid)>`) — production code never sets it (Postgres never runs as root on a real desktop install), but it exists so "must not run as root" fails as a clear, handled case rather than a cryptic Postgres-side error, and it's what lets this sandbox's own root-only CI environment run these tests against a real cluster at all (`sandbox_root_workaround_user`, itself a no-op on every real desktop install).

  **The lifecycle-model question this task deliberately left open — resolved: multiple instances, not a singleton.** Explicit product decision: "we might need multiple postgresses as needed — different versions need running, or the person genuinely needs separate postgres — let's not limit." `PostgresInstance` is a first-class domain record (`model.rs`), not owned by or limited to one per `OdooServer`; `Core` holds a registry (`HashMap<Uuid, PgSupervisor>`) of live supervisors alongside the SQLite-persisted static config, with `create_postgres_instance`/`list_postgres_instances`/`get_postgres_instance`/`start_postgres_instance`/`stop_postgres_instance`/`postgres_instance_state` methods, each `PgState` transition mapped to a `Postgres{Starting,Running,Stopping,Stopped,Crashed}` domain event. Wired into `orchestrator-api` as `/postgres-instances` (list/create/get) and `/postgres-instances/:id/{start,stop}`, and into a real Engine screen (`Engine.tsx`, replacing the former stub) that lists/creates/starts/stops any number of instances.

  **Verified against real installed Postgres, not a mock, at every layer**: `postgres.rs` — 7 tests, including a real `kill -9` sent to the running postmaster out-of-band, confirming the health watcher notices and transitions to `Crashed`, and a listener test confirming every transition fires including that crash; `lib.rs` — a `Core`-level test that creates two distinct `PostgresInstance`s with different ports/data-dirs and starts/stops them independently through `Core`, asserting neither's state or lifecycle affects the other (the concrete proof of "let's not limit"); and a genuine Playwright browser test driving the real Engine screen end-to-end — creating two instances, starting both (independently), stopping both (independently), confirming distinct PIDs/ports/versions throughout.

  **What's left before this is fully "done":** wiring into the actual Tauri sidecar mechanism once a desktop environment exists (0.7) — the supervision and multi-instance logic itself no longer needs a product decision or a desktop to validate, only the sidecar packaging does.

- **2.2 `uv`-managed Odoo runtime supervisor (L)** — *Done — including the wiring into `Core`, verified against a real Odoo checkout.* Two generic building blocks plus the domain wiring on top:

  `orchestrator-core::python_runtime` provisions an app-owned Python + venv via `uv` (per the runtime-architecture doc's decision) and installs a requirements list into it, applying the two Odoo-specific landmines that doc found: `psycopg2` (what Odoo pins) has no Linux/macOS PyPI wheels, so it's transparently substituted with `psycopg2-binary`; `python-ldap` has no wheels anywhere, so it's dropped on non-Windows (Odoo already excludes it on Windows). **Verified for real**: `uv python install` into an app-owned directory (not wherever `uv` would otherwise put it), a real `uv venv`, and a real `uv pip install psycopg2==2.9.9` that actually installs and imports `psycopg2-binary` — not asserted, executed. 7 tests (5 pure-logic on the substitution rules, 2 against real `uv`/PyPI).

  `orchestrator-core::odoo::OdooSupervisor` supervises a generic Python server process with the same state-machine shape as `PgSupervisor` (`Stopped → Starting → Running → Stopping → Crashed`) and a `with_listener` hook, but is genuinely different under the hood, not a copy-paste: `pg_ctl` daemonizes and hands back a pidfile, so `PgSupervisor` never holds the live process; `odoo-bin` runs in the foreground, so `OdooSupervisor` keeps the actual `tokio::process::Child` for its whole life, reads its stdout **and** stderr continuously and forwards each line to the listener (the process log this project's event system exists to surface), and detects a crash by directly observing `child.wait()` rather than by polling a readiness command — immediate, not bounded by a health-check interval. Readiness is a raw TCP-connect-and-minimal-HTTP-request probe against the configured port (no HTTP client dependency needed to prove "something HTTP-shaped is listening"). Stop is graceful `SIGTERM` with a `SIGKILL` escalation if the process doesn't exit within `shutdown_timeout`, matching Postgres's own "fast, don't babysit clients" posture. **Verified against a real subprocess, not a mock**: 6 tests — full lifecycle, double-start rejection, no-op stop, log lines streamed from both stdout and stderr, a real out-of-band `kill -9` correctly transitioning to `Crashed`, and a startup-timeout case that confirms the never-ready process actually gets killed.

  **The `Core` wiring, done on a real local desktop against a real Odoo 17.0 checkout** (the earlier cloud-sandbox session's egress policy blocked GitHub, the only place real Odoo source is distributed from — this needed a machine with one already on disk, or normal outbound network access to clone one): a new `orchestrator-core::odoo_conf` module renders a real `odoo.conf` from a server's registered addons sources (in `rank` order) and its assigned, running `PostgresInstance`; `Core::start_server`/`stop_server` spawn and supervise real `odoo-bin` through `OdooSupervisor`, with `OdooServer::state` (unlike `PostgresInstance`'s, which stays purely in-memory) persisted to SQLite on every transition via a new `Db::update_server_state`, and matching `POST /servers/:id/{start,stop}` routes. Deliberately explicit-params, same posture as `create_snapshot`'s filestore args: `start_server` takes the checkout root and an already-provisioned venv interpreter as plain arguments rather than inferring or provisioning either itself — provisioning stays a separate, explicit `python_runtime` call the caller makes first.

  **Two real Odoo/Postgres compatibility issues found and fixed along the way, not glossed over:** real Odoo hard-refuses to start (`"Using the database user 'postgres' is a security risk, aborting."`) when its own `db_user` is the cluster's superuser role — which every other Postgres-touching `Core` method deliberately *does* connect as — so a new `pg_admin::ensure_role` gives Odoo its own dedicated non-superuser `odoo` role instead; and recent `setuptools` releases (81+) dropped `pkg_resources`, which Odoo's own code (`odoo/modules/module.py`) imports directly, so the provisioned venv pins `setuptools<81`.

  **Verified end-to-end against a real Odoo 17.0 checkout, not a stand-in**: a new `Core`-level test registers the checkout's own addons directory as a server's `Core`-kind addons source, provisions a real venv (or reuses an already-provisioned one via `ORCHESTRATOR_TEST_ODOO_VENV_PYTHON`, keeping the test fast on repeat runs), starts real `odoo-bin` through `Core::start_server`, confirms it's actually serving HTTP and that `OdooServer::state` reads back `Running` through `Core::get_server` (not just held in-memory), then stops it and confirms `Stopped`. Also manually verified outside the test harness first (ran real `odoo-bin` by hand, `curl`'d it, got a genuine `303 → /web` redirect with a session cookie) before trusting the automated version.

- **2.3 Database lifecycle commands (M)** — *Done, and it resolved 2.2's other open item along the way.* `orchestrator-core::pg_admin` is a set of generic, Odoo-agnostic Postgres admin operations built directly on 2.1's real running instances — deliberately not Odoo-specific, since none of `createdb`/`dropdb`/`pg_dump`/duplicate-via-template know or care what's inside the database: `database_exists` (via `psql`), `create_database`, `drop_database` (`dropdb --if-exists`), `duplicate_database` (force-disconnects any other backends on the source with `pg_terminate_backend`, then `CREATE DATABASE ... TEMPLATE ...` — Postgres refuses to template a database with active connections, so this is a real constraint this project had to design around, not a nicety), `dump_database` (plain-SQL `pg_dump --file`), and `restore_database` (fresh `createdb` then replay the dump through `psql`). `Core` wires all five into real methods (`create_database` — now genuinely async and Postgres-backed instead of a bare SQLite insert, `duplicate_database`, `drop_database`, `backup_database`, `restore_database`), each validating its target server's `PostgresInstance` is actually running first (`CoreError::PostgresInstanceNotRunning` otherwise) and emitting the matching `Database{Created,Duplicated,Dropped,BackedUp,Restored}` event. Exposed via `orchestrator-api` as `POST /databases/:id/duplicate`, `DELETE /databases/:id`, `POST /databases/:id/backup`, and `POST /servers/:id/databases/restore`.

  **This is also what resolved 2.2's open "which `PostgresInstance` does a server use" question**: `OdooServer` now carries a required `postgres_instance_id`, validated to exist at `create_server` time — the caller decides per the topology rule in `odoo-orchestrator-runtime-architecture.md` (share by default when nothing forces separation, a dedicated instance only when something genuinely does), rather than `Core` silently assuming "the only instance."

  **Verified against real running Postgres clusters and real data, not mocks, at every layer**: `pg_admin.rs` — 3 tests, including a full dump→drop→restore round trip and a duplicate test that inserts a real row, duplicates the database, and confirms the row is present in the copy *and* that the source survives being used as a template; `lib.rs` — 6 new/rewritten `Core`-level tests covering scoping-to-server, rejection when the instance isn't running, duplicate/drop/backup/restore all exercised through `Core`'s real async methods against a real Postgres instance it starts itself; and a genuine end-to-end pass driving the real running API over HTTP with `curl` (create instance → start → create server → create database → insert a real row via `psql` → duplicate over the API → verify the row in the copy → back up over the API → drop the original over the API → confirm it's gone from Postgres → restore the backup over the API into a new database → verify the row survived), plus a from-scratch Playwright browser test (`e2e_database_lifecycle.mjs`) driving the same full lifecycle through the actual Topology screen's new Duplicate/Backup/Restore/Drop buttons (window prompts/confirms handled via Playwright's dialog interception) against the real running shell binary. 56 tests total in `orchestrator-core`, full workspace `cargo test` and `cargo build --workspace` green, frontend `tsc -b` and `vite build` both clean.

- **2.4 Module install/upgrade/uninstall commands (M)** — *Done, verified end-to-end against a real Odoo 17.0 checkout.* Scoped per-database (not per-server, since `ir_module_module` state is per-database even though the addons-path is shared): `Core::install_modules`/`upgrade_modules`/`uninstall_modules` reuse `start_server`'s `odoo.conf`-rendering preamble, then run real one-shot commands rather than `OdooSupervisor`'s long-running state machine (a new `odoo::run_one_shot` primitive — spawn, optionally pipe a script to stdin, capture output, report exit status — since these commands run to completion and exit, they don't need readiness-polling or crash-detection at all). Install/upgrade go through `odoo-bin -i`/`-u module1,module2 --stop-after-init --no-http` — installing against a bare (never-Odoo-initialized) database is a completely valid input, since every module depends on `base`, so `-i` on a fresh database bootstraps the whole framework as part of installing the first module, exactly like a real production database's first install. Uninstall has no CLI flag at all, so it goes through `odoo-bin shell` fed a real `env['ir.module.module'].search(...).button_immediate_uninstall()` call on stdin instead — the same non-interactive mechanism `click-odoo-contrib`'s own tooling uses under the hood. `upgrade_modules` reports each module's real post-upgrade `ir_module_module.latest_version` on its event, read back via a new `pg_admin::query_scalar`, not a fabricated one — this project's "no fake progress" rule applies to that number too. Matching `POST /databases/:id/modules/{install,upgrade,uninstall}` routes, same explicit-params posture as 2.2 (checkout root and a provisioned venv are plain request fields, not inferred or provisioned inline).

  **A third real Postgres/Odoo compatibility issue found and fixed**: Postgres 15+ revoked the default `CREATE`-on-`public`-schema privilege every earlier version granted non-owner roles, so 2.2's new `odoo` role could log in fine but then fail with `permission denied for schema public` the instant Odoo tried to create its first table — a new `pg_admin::grant_schema_privileges`, called per-database (schema privileges are per-database, so this can't be a one-time `ensure_role`-style setup step), fixes it.

  **Verified end-to-end against a real Odoo 17.0 checkout, not mocks**: a `Core`-level test creates a bare database, installs a real, genuinely small module (`google_account` — a minimal dependency chain, so it doesn't pay for a heavy module's own asset bundling on top of the unavoidable framework bootstrap) and confirms `ir_module_module.state` actually reads `installed` afterward (not just that the command claimed success), upgrades it and confirms a real non-placeholder version came back on the emitted event, then uninstalls it and confirms `ir_module_module.state` actually reads `uninstalled`. This is also what unblocks the Modules screen's deferred currency instrument (see 1.5 above) — see 2.5.
- **2.5 Wire into `orchestrator-api` + frontend (M)** — *Done.* Postgres instances (create/start/stop/status — 2.1), the full database lifecycle (create/duplicate/backup/restore/drop, with a Postgres-instance picker on server creation — 2.3), real server start/stop and module install/upgrade/uninstall routes (2.2/2.4), and now the frontend side of all of it are wired end to end.

  `Topology.tsx` gained real Start/Stop controls per server, backed by a new shared `OdooRuntimeSettingsPanel` (checkout root, provisioned venv python, runtime dir — the same three explicit local paths `Core::start_server`/module commands need, entered once and persisted in `localStorage`, not re-typed per action). `Modules.tsx` gained a per-database picker (module state is per-database even though the scan is per-server), real Install/Upgrade/Uninstall buttons per module row sourced from `Core::database_module_states`, and the real "N up to date" currency instrument the Modules screen had been deferring since 1.5 — computed by comparing each scanned module's manifest `version` against its database's real `ir_module_module` version, using Odoo's own real version-adaptation rule (`odoo/modules/module.py`'s `adapt_version`: a missing version defaults to `"1.0"`, then gets prefixed with the server's own major series unless already prefixed) replicated client-side rather than guessed, since a naive direct string comparison would have reported nearly every real module as perpetually out of date.

  **Verified against the real running API, a real browser, and real `odoo-bin`, not mocks**: a new Playwright script (`e2e_server_and_module_commands.mjs`) drives a real server through Start (confirmed via a real `curl` to the now-running port, not just the UI's own claimed status) then Stop, and drives a real module (`google_account`) through Install → confirms `UP TO DATE` and the currency instrument correctly reads "11 of 559" (the framework's real pulled-in dependencies, not just the one module clicked — proof the version-adaptation comparison works across many real modules, not one lucky case) → Uninstall → confirms it reverts to "not installed". ## Workstream 3 — Branch-based snapshotting — **done**

- **3.1 Postgres template-DB + filestore snapshot primitive (M)** — *Done.* A `Snapshot` domain record (`model.rs`) combines two things taken together as one named, point-in-time-frozen artifact: (a) a real Postgres database duplicate, reusing 2.3's `pg_admin::duplicate_database` mechanism exactly rather than reimplementing it, and (b) an optional hardlink-based directory snapshot of a filestore, via a new, fully generic `orchestrator-core::filestore` module (`snapshot_directory`/`remove_snapshot_directory`) that hardlinks every regular file (instant, metadata-only, same-filesystem-only — `std::fs::hard_link`), recreates the directory structure, and recreates symlinks as symlinks rather than following them. `Core::create_snapshot` derives a collision-free Postgres database name for each snapshot (`derive_snapshot_database_name`: sanitize the source name, append a fresh UUID), duplicates the source database, optionally snapshots a filestore directory via `spawn_blocking`, persists the `Snapshot` row, and emits `SnapshotCreated { has_filestore }`; `Core::delete_snapshot` drops the snapshot's own Postgres database, removes its filesystem copy if present, deletes the row, and emits `SnapshotDeleted`. Exposed via `orchestrator-api` as `POST`/`GET /databases/:id/snapshots`, `GET /snapshots`, and `DELETE /snapshots/:id`; wired into `Topology.tsx` with a "Snapshot" action per database (prompts for a name) and an indented per-database list of existing snapshots, each with its own "Delete" action and a `(+filestore)` flag when applicable.

  **A deliberate design decision, proven rather than just asserted**: `Snapshot` stores `server_id` directly, not only `database_id`, so a snapshot stays fully usable (listable, deletable) even after its *source* `Database` is dropped — `delete_snapshot` reaches Postgres via `get_server(snapshot.server_id)`, never via `get_database(snapshot.database_id)`. A dedicated test, `snapshot_survives_and_stays_deletable_after_its_source_database_is_dropped`, actually drops the source database mid-test and confirms the snapshot's own database and (if present) filesystem copy can still be cleanly deleted through `Core` afterward. The `snapshots` table's `database_id` column deliberately has no foreign key for the same reason (see 0.3's update).

  **The filestore half is honestly scoped, same posture as 2.2's Odoo gap**: `filestore.rs` is fully generic — it snapshots any directory tree, with no Odoo-specific knowledge — and its module doc comment is explicit about *why* hardlinking happens to be safe for Odoo's real filestore (content-hash-addressed, files only ever added/removed, never edited in place) without the code itself assuming or verifying that property; the test suite proves both the safe pattern (delete+recreate in the source doesn't affect an existing snapshot) and the unsafe one (editing a file in place after snapshotting leaks through the shared inode, by design). Since there's no real Odoo filestore anywhere in this project yet, `create_snapshot`'s filestore parameters are both `Option`, and the frontend's "Snapshot" action deliberately never prompts for a filestore path today — the primitive is built and genuinely tested against real synthetic directories with real files, just not wired to a nonexistent real target, matching the "no fake progress" rule applied to 2.2 and 2.3's own scope cuts.

  **Verified against real Postgres and a real filesystem, not mocks, at every layer**: `filestore.rs` — 8 tests, including hardlink-identity confirmed via inode number (`std::os::unix::fs::MetadataExt::ino()`), the in-place-edit leak, symlink recreation, empty directories, and rejection of a missing source or an already-existing destination; `lib.rs` — 7 new `Core`-level tests: duplicating real inserted data while confirming the snapshot keeps the old value after the source is mutated afterward, hardlinking real files into a real filestore snapshot, deleting a snapshot and confirming both its database and its filesystem copy are actually gone (`get_snapshot` then returns `NotFound`), the source-dropped-survival test above, scoping `list_snapshots` to one database among several, and the `SnapshotCreated`/`SnapshotDeleted` events firing with the correct `has_filestore` flag; a genuine end-to-end pass driving the real running API over HTTP with `curl`+`psql` (insert real data → snapshot over the API → mutate the live database → confirm the snapshot's own database still has the old value — the headline "frozen, not a live view" claim, proven for real); and a Playwright browser test (`e2e_snapshot.mjs`) driving the real Topology screen's Snapshot/Delete buttons end to end against the real running shell binary (window prompts/confirms handled via dialog interception), confirming the UI wiring drives the same server-side mechanism already proven at the lower layers.

- **3.2 Git-branch binding (M)** — *Done — and turned out not to be genuinely blocked on anything this sandbox lacked.* This doc previously described 3.2 as blocked on "a real git repo to link against" as if that meant GitHub access, conflating it with 2.2's very different, genuinely-still-blocked GitHub constraint. On inspection, this task only ever needed the local `git` CLI (present in this environment, `git version 2.43.0`) and *a* real git working directory — which `git init` in a tempdir creates for free, no network involved. That distinction matters: 2.2 needs a real *published* Odoo source it cannot fetch (a real external dependency), while 3.2 needs only a real *local* repository, something this sandbox — or any environment — can always produce for itself. Reusing the existing `Private`-kind `AddonsSource` as "the linked repo" (rather than inventing a new per-server "repo path" concept, and rather than waiting on Workstream 4's unrelated openvscode-server work as this doc previously implied) made this buildable immediately: an `AddonsSource` with `kind: Private` was already, in this codebase's own words from an earlier test, labeled `"this repo"`.

  A new, fully generic `orchestrator-core::git` module (same posture as `pg_admin.rs`/`filestore.rs` — no Odoo-specific knowledge) provides `current_branch(repo_path) -> Result<String, GitError>`, which runs the real `git -C <path> rev-parse --abbrev-ref HEAD` and distinguishes every real way this can fail rather than collapsing them: `NotARepo`, `NoCommitsYet` (an unborn-HEAD repo — real, observed `git` behavior where the command fails but still prints `"HEAD"` to stdout, which is exactly why this checks the exit code rather than trusting stdout blindly), and `DetachedHead` (a *successful* command that still has no branch name — `--abbrev-ref HEAD` prints the literal string `"HEAD"`). Deliberately uses `-C <path>` rather than requiring `path` to be a repo's root, since a real addons source's `path_or_url` is typically a *subdirectory* of a larger repo (the existing `~/repos/acme-odoo/addons` example already in this codebase) — `git` itself walks up to find the enclosing repo from any subdirectory, so this module doesn't need its own repo-root-finding logic.

  `Core::current_git_branch(server_id) -> Result<Option<String>, CoreError>` looks up the server's first `Private`-kind addons source (ignoring `Oca`/`Core` sources, which are vendor code a user doesn't typically branch) and collapses every honest "nothing to suggest" case (no private source registered, not a git repo, no commits yet, detached HEAD) to `Ok(None)` rather than an error — a snapshot's `name` has always been free-form text (see `Snapshot`'s own doc comment), so a missing suggestion is a normal, handled case exactly like 2.2's missing Odoo checkout or 0.6/0.7's missing desktop, not a failure. Exposed via `orchestrator-api` as `GET /servers/:id/git-branch` (`{"branch": null}` is a completely normal response, not an error). `Topology.tsx`'s "Snapshot" action now calls this before prompting and prefills the prompt's default value with the real branch name when one is found, falling back to the previous generic default ("pre-migration") otherwise — still a free-editable prompt, not a forced binding, matching `Snapshot.name`'s "any string is valid" design from 3.1.

  **Verified against a real `git` binary and real repositories, not mocks, at every layer**: `git.rs` — 7 tests, including a real branch switch, a real `init.defaultBranch` other than "main" (proving nothing here hardcodes an assumed default), the subdirectory-walk-up case (the realistic shape, matching how addons sources are actually registered), a real detached HEAD via checking out a bare commit SHA, and a real zero-commit repo; `lib.rs` — 5 new `Core`-level tests covering no-private-source, a real linked repo on a real branch, a private source that isn't a git repo, an `Oca`-kind source being correctly ignored even though it *is* a git repo, and an unknown server id; a genuine end-to-end pass driving the real running API over HTTP with `curl` (branch is `null` before any addons source is registered → register a real `git init`'d repo's subdirectory as a `Private` addons source → branch now correctly reports the real checked-out branch name, resolved from the subdirectory path, not the repo root); and a Playwright browser test (`e2e_git_branch.mjs`) that captures the actual `window.prompt()` dialog's `defaultValue` — not just that a dialog appeared — confirming it's genuinely prefilled with the real branch, then accepts it and confirms the resulting snapshot is actually named after that branch. 88 tests total in `orchestrator-core` (up from 76), full workspace `cargo build`/`cargo test` green, frontend `tsc -b` and `vite build` both clean, no leaked Postgres or shell processes after any run.

- **3.3 Named snapshots + one-click revert (M)** — *Done.* `Core::revert_database_to_snapshot` restores a database's *current* Postgres database (and, when a `filestore_target` is given, a filestore directory) **in place** from an existing `Snapshot` — genuinely distinct from two similar-sounding operations already in this file: 3.1's `create_snapshot`/`delete_snapshot`, which only ever create or remove a frozen side copy and never touch a live database, and 2.3's `restore_database`, which replays a `pg_dump` file into a brand-new database and never overwrites an existing one. The mechanism: drop the live database, then `CREATE DATABASE ... TEMPLATE` straight from the snapshot's own database — reusing `duplicate_database` a second time (3.1 already reused it once from 2.3), direction reversed. The `Database` row itself is untouched (same id, same name); only what Postgres holds under that name changes. Validates the snapshot actually belongs to the database being reverted (`CoreError::SnapshotNotForDatabase` otherwise) and that a `filestore_target` is only accepted when the snapshot actually has a filestore half (`CoreError::SnapshotHasNoFilestore` otherwise).

  **The friction ladder's rung for this exact action — "Restore snapshot over live DB" — calls for a counter-snapshot to be offered before the destructive step, and that's implemented for real, not just promised in a dialog**: when a `counter_snapshot_name` is given, `revert_database_to_snapshot` takes one real snapshot of the live database (via `create_snapshot`, not reimplemented) *before* dropping it, and returns that snapshot to the caller — so if this fails, the live database is never touched, and if it succeeds, the caller has in hand exactly what the revert can itself be undone with. The counter-snapshot is deliberately database-only (no filestore half captured automatically) — same "don't pretend to capture what wasn't asked for" posture as `create_snapshot`'s own filestore parameters, and consistent with there being no real Odoo filestore in this project to snapshot as a matter of course.

  **Applied the friction-ladder confirmation copy from `odoo-orchestrator-ui-design-principles.md`**: the "Revert to this" action's confirmation dialog carries all four required elements — named object (the database and snapshot names), quantified consequence ("permanently overwrites `<db>`'s current data with the snapshot's"), reversibility status (names the counter-snapshot that will be taken first), and ripple effects ("nothing else on server `<name>` is touched"). One honest, called-out UI limitation: native `window.confirm()` can't relabel its own button to name the action (`Restore pre-migration-2`) the way the design doc's ideal calls for — that needs a real custom dialog component this screen doesn't have yet — so the message body carries all four elements while the button itself still just says "OK."

  **Verified against real Postgres and a real filesystem, not mocks, at every layer**: `lib.rs` — 5 new `Core`-level tests: `revert_database_to_snapshot_restores_real_data_in_place` mutates the live database after snapshotting, reverts, and confirms the live data is back to the snapshot's frozen value (the headline claim); `revert_database_to_snapshot_takes_a_real_counter_snapshot_when_asked` confirms the counter-snapshot actually captures the *pre-revert* live state, not the target snapshot's state, and that it's a real, listable snapshot afterward; `revert_database_to_snapshot_rejects_a_snapshot_from_a_different_database` and `revert_database_to_snapshot_rejects_filestore_target_when_snapshot_has_none` cover both validation errors; `revert_database_to_snapshot_with_filestore_hardlinks_the_snapshots_files_into_target` confirms a real, differently-populated "live" filestore directory is actually replaced (not merged) with the snapshot's hardlinked files. A genuine end-to-end pass driving the real running API over HTTP with `curl`+`psql` (insert real data → snapshot → mutate the live database → revert over the API with a counter-snapshot name → confirm via `psql` the live database is back to the snapshot's value → confirm via `psql` the counter-snapshot has the pre-revert value → confirm a mismatched-snapshot revert is rejected with 422), plus a Playwright browser test (`e2e_revert.mjs`) driving the real Topology screen's new "Revert to this" button end to end — including capturing the actual `window.confirm()` dialog text and asserting all four friction-ladder elements are genuinely present in it, not just that the button was clicked through.

**Update — a real bug found by running the Odoo tests in the cloud sandbox
(now that its egress reaches GitHub again).** The two real-Odoo tests had
been *skipping* in every sandbox session — they guard on
`ORCHESTRATOR_TEST_ODOO_CHECKOUT` and count as `ok` when it's unset — so
"118 tests pass" said nothing about them. Run for real against a fresh
Odoo 17.0 clone, they exposed that `initdb` was invoked with no
`--encoding`: on a machine whose locale isn't UTF-8 the app produced a
`SQL_ASCII` cluster, and **Odoo cannot initialize any database on one**.
It passed on the desktop where 2.4 was originally verified purely because
that machine exports `LANG=en_US.UTF-8`. Fixed in `postgres.rs` and
`pg_admin.rs`, with a direct regression test
(`every_database_this_app_makes_is_utf8_whatever_the_machine_locale`);
full write-up in `odoo-orchestrator-real-odoo-findings.md`.

That investigation also found and fixed a **second** real bug: dropping
the PostgreSQL supervisor left its server running — and a naive `Drop`
would never have fired, because the background health watcher held a
strong clone of the supervisor it was watching. The watcher now holds a
weak reference, the last handle stops the cluster, and `start()` adopts a
postmaster left behind by a hard kill rather than colliding with it. A
third claimed finding (that provisioning needs system build headers) was
checked and found **wrong** — the app already substitutes
`psycopg2-binary` and drops `python-ldap`, so it never compiles either
from source; that is recorded in the same doc rather than deleted.
